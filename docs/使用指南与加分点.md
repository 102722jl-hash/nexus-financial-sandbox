## 一、这个项目是什么

一句话：**把"行业数据"编译成"可调节、可复算、可追溯的金融传导网络"的沙盘。**

它解决的是传统行业研究/财务模型的三个痛点：

| 痛点 | 本项目的做法 |
|---|---|
| 模型是黑盒，改了参数不知道为什么变 | 每条边都挂公式与证据，可复算血缘（CALCULATED LINEAGE） |
| 数据来源说不清，无法审计 | 每个观测点回指原始快照，且哈希必须自洽 |
| 换一个行业就要重写一套系统 | 六层网络语义完全动态，同一引擎套所有行业 |

三种典型使用姿势：

1. **只做推演**——打开浏览器调变量看结果（不需要数据库、不需要采集器）
2. **接自己的库**——用"数据接入"面板把只读 PostgreSQL 表映射成网络
3. **新增行业板块**——用 Skill 驱动设计 + 采集器落地 + 确定性编译器入网

## 三、核心概念（看懂这 8 个词就够了）

| 概念 | 含义 |
|---|---|
| **网络 Network** | 一个行业的传导图，如 `coal_power_v1`（煤炭价格 → 火电企业盈利） |
| **层 Layer** | 网络的纵向阶段，默认六层：外部驱动 → 供需 → 价格 → 经营 → 财务 → 估值 |
| **节点 Node** | 层里的一个可观测/可调节量，带 `baseline`、`editable`、`valueStatus` |
| **边 Edge** | 节点之间的传导关系，带 `weight`、`formulaType`、`formulaParameters`、`impact_cap_pct` |
| **证据 Evidence** | 支撑某条边的原始材料，含 `source_url`、`publisher`、`published_at`、`original_quote`、`locator`、`snapshot_path`、`snapshot_sha256` |
| **批次 Batch** | 采集端交付给沙盒的标准数据包，契约版本 `nexus-crawler-batch-1.0.0` |
| **三道门禁** | `DATA_READY` / `GRAPH_READY` / `SCENARIO_READY`，把"能看"和"能算"严格分开 |
| **状态三态** | `CONFIRMED` 进计算、`CANDIDATE` 只展示、`ABSTAIN` 不输出 |

传导计算的基本式：

```text
target_change = source_change × direction × weight × time_factor
```

## 四、设计想法与演进：从"事后找关系"到"采集端分类"

> 这一节记录的是**为什么项目会长成现在这样**。理解了这条演进线，后面那些"契约、表角色、语义层、门禁"就不是设计洁癖，而是被现实问题一步步逼出来的。

### 4.1 最初的设想：让库表之间的关系看得见

原始目标很朴素——把每天采集到的金融数据，用**网络沙盘**的形式，把各张表、各个字段之间的关系清晰地标出来，让"煤炭价格涨了 → 火电经营承压 → 公司盈利变化 → 市场估值重估"这样一条链一眼可见。

文档里的原始表述：

- `DATABASE-TO-NETWORK-PACK-PROMPT.md`：「只读读取原始表、字段、注释和样例 → **从混乱或清晰的数据中识别网络信息** → 清洗、中文化、拆分并标准化多张表 → 生成可直接导入金融世界沙盒的网络数据包」
- `NETWORK-DATA-PACK-AI-GUIDE.md`：「识别表和字段角色 → …… → **校验跨表关联** → 生成因果网络和完整证据网络」

关键词是"**识别**"和"**从混乱中**"——最初的设计假设是：**关系本来就藏在数据里，只是需要被读出来。**

### 4.2 撞上的墙：跨表语义对不齐

这个假设很快被现实打脸。文档里散落的问题记录还原了当时的困境：

| 症状 | 出处 |
|---|---|
| 「字段语义冲突」 | `financial-world-sandbox-multi-industry-design.md` §517 |
| 「同一证据 ID 的关键字段冲突」 | 同上 §713 |
| 「公司、行业或指标映射有歧义」 | 同上 §709 |
| 「币种、单位、期间或报表口径冲突」 | 同上 §710 |
| 「节点分类错误或总标题错误」「新数据进入数据库后网络结构残缺」 | `SIDE-CONVERSATION-TASK-SUMMARY.md` §31-38 |
| 「节点 ID 重复、关系引用不存在节点、network_id 混用、单位/币种不一致和数据截止日越界」 | `NETWORK-DATA-PACK-AI-GUIDE.md` §345 |

结论是：**问题不在识别算法，而在数据源头就没有统一语义。** 同一件事在不同表里叫不同名字、用不同单位、算在不同口径下，"事后在多表之间找关系"这件事在源头就注定做不对。

### 4.3 第一次转向：把分类前移到采集端

核心调整：**不再指望事后对齐，而是在采集入库时就按类别把数据写进规范字段。**

三个具体动作：

1. **给每张表定"角色"**。判定依据是字段签名、注释、样例值和表名，而不是靠表名猜。

   | 角色 | 存放内容 |
   |---|---|
   | REGISTRY | 网络名称、版本、状态、截止日 |
   | LAYERS | 各层标题、顺序、副标题 |
   | NODES | 节点定义、基准值、可编辑状态 |
   | EDGES | 节点间传导关系与参数 |
   | ENTITIES | 公司、银行、产品、地区、项目 |
   | METRICS | 实际指标、行业数据、财务数据 |
   | FORMULAS | 确定性公式与参数 |
   | EVIDENCE | 数值与关系的来源 |
   | VALUATION | 市值、基准价值、情景价值 |
   | UNKNOWN | 无法可靠归类（V2 新增，不强行塞进某个角色） |

   同时允许缺表：「用户不必提供全部表。缺少某张表时继续处理其他角色」。

2. **拆分与标准化**，并立下一条硬规则：**「同一字段不能因为名称相似就重复写入多个角色」**——这正是为了根治"字段语义冲突"。

3. **字段级映射表落地**。`coal_network_collector/FIELD-MAPPING.md` 用「页面内容 → `metric_code` → 目标表」三列把映射固化下来，让"分类"从口头约定变成可检查的清单。

### 4.4 第二次收口：用契约把规范锁死

分类还不够——采集端与沙盒端之间还需要一份双方都无法私自更改的"合同"。

- **三层分工**：RAW（原始快照）→ STANDARD（标准批次）→ NETWORK（网络），各层职责不重叠。
- **冲突消解写进规则**：「`weight / candidate_weight` 始终填写正数幅度；正向或负向只能由 `direction` 表示，**禁止在权重中重复写负号**」——把"方向"和"强度"两个维度彻底拆开，杜绝负权重带来的歧义。
- **稳定 ID 从根上消除重复**：「所有 ID 使用规范化字段生成 SHA-256，避免重复爬取产生新记录」。
- **分级处置**：单条对象的问题只隔离那一条；只有批次级问题才阻止整批进入网络。**避免"一条脏数据毁掉一整天的采集"。**
- **机器可校验**：Schema 设 `additionalProperties: false`，字段级与跨对象引用（`evidence → document_id`、`observation → evidence_id`、`relation → formula_id`）逐条校验，不合法直接 `CRAWLER_BATCH_BLOCKED`。

### 4.5 第三次转向：把"六层语义"也解耦

规范化的副作用很快显现：为了让流程确定，早期版本**把六层含义写死了**（第 4 层就是公司、第 6 层就是估值），换个行业就对不上，于是出现"节点分类错误、总标题错误"。

V2 数据包指令明确推翻了这一点：

> 「画布固定为六列，但**六层业务含义不能写死**。`layer_no` 只表示从左到右的位置，具体语义由当前网络的 `network_layers` 生成」
> 「不得固定第 4 层一定是公司或第 6 层一定是估值……必须标记 `AI_CANDIDATE` 并进入 `review_queue`」

配套引入 `semantic_role` 与 `path_role`（`SOURCE / INTERMEDIATE / SINK`，契约侧另加 `EVIDENCE_ONLY`），并要求「网页分类必须读取该表，不得在前端写死行业层级名称」。

V2.20 的验收结论印证了这次转向：**「节点分类来自 `default_layer_code`；不再由网页根据字段名临时猜测。」**

这一步的意义：**位置与语义解耦后，"六层"从一种业务假设降级为一种版式约定**——于是同一套引擎才能同时跑焦煤、新能源汽车，以及之后的任何行业。

### 4.6 与不确定性共处，而不是假装它不存在

设计走到最后，剩一个绕不开的问题：遇到拿不准的数据怎么办？

- **三态隔离**：`CONFIRMED / ACTIVE / APPROVED` 才进入确定性计算；`CANDIDATE` 可以展示和解释，**但不能改变下游数值**；`ABSTAIN` 干脆不输出方向或精确数值。
- **审核队列显式化**：`review_queue` 至少包含 `object_type / object_id / candidate_value / confidence / reason / evidence_ids / required_action / review_status`——把不确定性当成一等公民记录下来。
- **不补零**：「不使用零值填补缺失值」「数据不足时降级或拒绝输出，不补零、不伪造精确估值」。

### 4.7 演进时间线

| 阶段 | 主要变化 |
|---|---|
| V1.0 / V1.1 设计基线 | 确立"通用引擎 + 领域包 + 适配器"；修订术语（"估值贡献" ≠ 公司估值） |
| V2.5 – V2.8 | 引入数据契约、领域包、只读 PostgreSQL 与时间门禁 |
| V2.9 – V2.12 | 通用图编译器、领域路由隔离，避免跨行业节点误用 |
| V2.13 – V2.14 | 严格估值门禁、情景市值重估 |
| V2.15 – V2.17 | 数据接入、规则/候选字段映射、只读连接器 |
| V2.19.9 – V2.19.12 | 本地字段分流（中文词典）、预编译网络表、AI 候选关系 |
| V2.19.13 | 公式别名归一化、未知公式只做局部隔离 |
| **V2.20** | 引入 `nexus-crawler-batch-1.0.0` 统一采集出口与三道门禁 |

**一句话概括这条主线**：最初想"事后在多表之间找关系"，发现源头语义不统一、救不回来；于是把**分类、映射、稳定 ID 全部前移到采集端**，再用**契约**锁死；接着把**位置与语义解耦**，让一套引擎通吃所有行业；最后用**三道门禁 + 三态审核 + 不补零**，让"能看"和"能算"彻底分离。

## 六、路径 B：接入自己的数据库

适用于：你已有行业库，想直接变成沙盘网络，不想写采集器。

### 6.1 前提

源库必须是 **只读账号**。本项目全程遵守"不写回源库、不补零、不推断缺失值"。

### 6.2 数据包指令（两种版本）

| 文档 | 差异 |
|---|---|
| `DATABASE-TO-NETWORK-PACK-PROMPT.md`（V1） | 给了示例层标题，容易被写死 |
| `DATABASE-TO-NETWORK-PACK-PROMPT-V2.md`（V2） | 要求**六层语义完全动态**；确认边必须 `formula_id` 存在 + `parameters_json` 完整 + `impact_cap_pct` 有限 + `evidence_id`；新增包状态与 `calculation_ledger`、`review_queue` |

**建议直接用 V2。**

### 6.3 操作步骤（摘自 `NETWORK-DATA-PACK-AI-GUIDE.md`）

1. 发现表和字段
2. 判断每张表的角色：`REGISTRY / LAYERS / NODES / EDGES / ENTITIES / METRICS / FORMULAS / EVIDENCE / VALUATION`
3. 按角色逐表校验
4. 建立表间关联
5. 生成六层
6. 生成 `causalGraph` + `fullGraph`
7. 判定传播资格：`CONFIRMED` 进计算、`CANDIDATE` 只展示、`ABSTAIN` 不输出

### 6.4 产出包的状态语义

`IMPORT_READY`（可入库）/ `SIMULATION_READY`（可推演）/ `PARTIAL`（部分可用）/ `INVALID`（不可用）。

包内**必须保留**：来源表名、列名、行键 + `data_cutoff`。包内**绝不包含**：数据库明文凭据。

### 7.4 第四步：门禁与发布

编译与入库都要过 `composite_quality.py` 的三道门禁：

| 门禁 | 判定 |
|---|---|
| `DATA_READY` | 有节点 且 必需指标覆盖率 ≥ **80%** |
| `GRAPH_READY` | 有节点 且 无结构性阻断（重复节点 ID、层级非法、边指向不存在节点、重复边 ID） |
| `SCENARIO_READY` | 前两者通过 且 至少存在一条"可调节点 → 可达结果终点"的可计算路径 |

通过后输出网络 JSON，`outputLevel` 为 `CANDIDATE_SCENARIO` 或 `GRAPH_ONLY`。发布规则：**只追加新网络，不自动切换当前页面**，旧版本保留可回滚。

### 7.5 快速原型（可选，绕过全部后端）

`multi-industry-sandbox-template` 是纯浏览器端静态沙盒（NEXUS DOMAIN LAB），无数据库、无 AI，浏览器内确定性推演。

扩展新行业 = 在 `domains.js` 的 `window.DOMAIN_PACKAGES.packages` 里追加一个领域包对象，字段：`id / name / version / state / cutoff / scenario / layers / nodes / edges / companies / source / mappings / insight`，复用六层定义即可，`app.js` 自动渲染。内置 `coal-steel` 与 `banking` 两个示例。适合做**对外演示与方案评审**，不适合生产数据。

## 十、加分点（这个项目真正值钱的地方）

### 1. 可复算血缘，而不是"看起来对"

每条被采纳的边都必须带公式参数与证据。界面上的 `CALCULATED LINEAGE`、`追溯` 面板可以直接把结果倒推回原始快照。传导公式统一为：

```text
target_change = source_change × direction × weight × time_factor
```

同类产品通常只给一个数字，这里给的是**一条可以自己验算的算式**。

### 2. 证据哈希自洽校验

证据的 `snapshot_sha256` 必须**等于**其文档的 `content_sha256`，否则校验直接不通过。这意味着"引用了一张图但图被换过"这种情况在结构上不可能发生。

### 3. 三道门禁把"能看"和"能算"彻底分开

覆盖率达到 80% 才 `DATA_READY`；结构无阻断才 `GRAPH_READY`；**必须存在至少一条可调节点 → 可达结果终点的路径**才 `SCENARIO_READY`。很多沙盘产品的失败模式就是"图很漂亮但点一下没反应"，这道门禁从机制上排除了它。

### 4. 确定性编译，同输入必同输出

编译器全程 `sorted` 排序（层按 `(sort_order, layer_no)`、队列与循环全排序），节点/边 ID 由 `stable_id(prefix, *parts)` 生成——对规范化 JSON 取 SHA-256 前 24 位大写十六进制。同一个批次编译两次，得到比特级一致的结果，并且记录 `graph_sha256 = sha256(canonical fullGraph)`。**可复现，可对账。**

### 5. 幂等入库，永不 TRUNCATE

所有写入都是 `INSERT ... ON CONFLICT DO UPDATE/DO NOTHING`，冲突键如 `document_id`、`observation_id`、`(network_id, node_id)`。重复跑同一批次不会产生脏数据，也不会清空历史。这在"每天定时采集"的场景下是刚需。

### 6. 候选 / 确认 / 弃权三态，AI 不许越权

策略常量写死在版本身份文件里：`AI_APPROVED_IS_CANDIDATE_AND_ABSTAIN`。AI 的判断**最高只能到 CANDIDATE**（只展示、不进计算），只有 CONFIRMED 才参与传播，ABSTAIN 完全不输出。把"AI 猜测"和"已确认事实"在数据结构层面分开，而不是靠文案提醒。

### 7. 凭据策略：密码以"引用"形式存在

`credentialPolicy = EPHEMERAL_OR_ENV_REFERENCE_ONLY`。入库脚本的 `--password-env` 传的是**环境变量名**，不是密码本身；数据包里明令禁止携带凭据；采集器本地存储用 DPAPI 加密（`.postgres-secrets.dpapi.json`，本机绑定，不可跨机器解密）。**审计时可以直接证明密码没有落盘到交付物里。**

### 8. 六层语义完全动态，一套引擎通吃全行业

V2 数据包指令规定：`layer_no` 只表示位置，层的语义完全由 `network_layers.semantic_role` / `path_role`（`SOURCE / INTERMEDIATE / SINK`）决定。因此"焦煤—火电"和"新能源汽车"用的是同一套引擎、同一套公式注册中心、同一套门禁，只是领域包不同。**新增行业的边际成本接近线性。**

### 9. 冻结版 + 哈希清单 + 版本注册表 = 可交付存档

v2.19.13 冻结版带 `VERSION.json` 身份文件与 127 条 `SHA256SUMS.txt`，配套 `NEXUS-VERSION-REGISTRY.md` 说明恢复规则。任何评审/验收场景下，"这个结果到底是哪个版本跑出来的"有确定答案，且可当场验证未被篡改。

### 10. 只读与不补零的克制

全程遵守不改动源库、不填充缺失值、不臆测数据。`review_queue` 承接所有拿不准的项（如新能源的 `PENDING` 审核队列），把不确定性显式暴露出来，而不是悄悄糊过去。**这是能通过严肃尽调的前提。**

### 11. 契约机器可校验，而非口头约定

`v220_crawler_payload.schema.json` 顶层 12 个必需键 + `additionalProperties: false` + `sha256` 正则约束，配合 `crawler_contract.py` 的字段级与跨对象引用校验（`document → source_code/batch_id`、`evidence → document_id`、`observation → evidence_id`、`relation → formula_id`）。采集端产出不合法，编译阶段直接 `CRAWLER_BATCH_BLOCKED`。

### 12. 数据源按 Tier 分级

T1 官方统计（统计局、能源局、交易中心）、T2 交易所与指定披露媒体公告、T3 行情代理。分级信息随数据源一起记录，便于对"证据强度"做差异化标注。
